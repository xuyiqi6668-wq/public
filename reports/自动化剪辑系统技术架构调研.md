# 用一份时间线驱动两条视频生产线

推荐的整体架构是**一份自定义、带版本号的时间线中间表示（IR），后面接多个编译后端**：真人口播和文案视频都先落成同一种 JSON 时间线，再分别编译到 Remotion（主合成引擎，同时负责浏览器预览）、FFmpeg（入库转码、切割、音频处理与 NVENC 编码）、剪映草稿（人工精修出口），以及可选的阿里云 IMS（国内托管渲染）。框架方面，Remotion 仍是生产风险最低的主引擎：它 2020 年开源，Lambda 分布式渲染成熟，预览和成片用同一套组件，Submagic、Crayo 等同类 AI 短视频产品都建在它上面。HeyGen 的 HyperFrames（Apache-2.0，2026-04-16 公开发布，已有约 7.4 万星）在 agent 友好性和零授权费上占优，但项目只有约 6 个月，仍是 0.x 版本，更适合做模板研发工具和授权对冲，前提是 IR 不绑定任何一家引擎。口播链路的质量上限取决于中文字级时间戳的精度（Qwen3-ForcedAligner 中文对齐误差约 33 ms），剪辑决策应采用混合模式：确定性规则处理静音和口癖，LLM 只输出引用词 ID 的删除和强调操作，再由编译器算出帧精确的切点。文案视频链路则用 TTS 的真实时长回填分镜，成本主要取决于视觉素材怎么选。按研究员测算，5 分钟口播的边际云成本约 0.8–2 元，ASR 和 LLM 只占几毛钱；60 秒文案视频从约 0.2 元（全库存素材）到数十元（全 AI 视频）不等，真正昂贵的是人工复核时间。合规方面，自 2025-09-01 起，凡用到 TTS、数字人或 AI 画面的成片，都必须同时加显式标识和文件元数据隐式标识，克隆声音或形象还须取得本人单独同意。落地建议分四步：先用托管 API 跑通口播 MVP，再加文案视频模板和合规模块，然后补齐重构图、B-roll、VLM 质检和自托管模型，最后做长转短和规模化。

> 标注约定：价格默认取自厂商官方页面。“（第三方）”表示数字来自转售商、聚合站或第三方整理；“（测算）”表示研究员或本报告按公开单价自行换算的结果，汇率按 1 美元 ≈ 7.1 元（研究员的假设）。笔记之间有四处互相矛盾：阿里云 IMS 价格、NVENC 会话上限、HyperFrames 的发布日期与星数、剪映草稿是否加密，各处的取舍在相应章节逐一说明。

## Remotion 当主引擎，FFmpeg 扛重活，HyperFrames 做对冲

Remotion 和 HyperFrames 的底层管线几乎一样：在无头 Chrome 里逐帧定位、截图，再交给 FFmpeg 编码。所以两者都能做到帧精确，也都受“逐帧截图”这个瓶颈约束（[Remotion Lambda limits](https://www.remotion.dev/docs/lambda/limits)；[HyperFrames 确定性渲染](https://hyperframes.heygen.com/concepts/determinism)）。真正的差别在三处：作者模型、授权和成熟度。

Remotion 把视频写成以帧号为自变量的 React 组件。**最新版 4.0.539 发布于 2026-10-26**，大约每周两三个版本；GitHub 有 **68,141 星**，2026 年 6 月 npm 月下载约 487 万次（[npm: remotion](https://registry.npmjs.org/remotion)；[GitHub](https://github.com/remotion-dev/remotion)；[npm downloads](https://api.npmjs.org/downloads/point/last-month/remotion)）。2024–2026 年它补上了几块和本系统直接相关的能力：`@remotion/media` 里的 `<Video>` 组件基于 WebCodecs/Mediabunny，只下载、只解码需要的帧，已是官方推荐用法；`@remotion/captions` 字幕栈支持五种转写后端；浏览器端渲染从 4.0.491 起标为稳定；此外还有官方 Agent Skills 和各编码助手插件。托管的 MCP 服务器则已于 2026-10-26 关停（[Video 文档](https://www.remotion.dev/docs/media/video)；[Transcribing](https://www.remotion.dev/docs/captions/transcribing)；[Client-side rendering](https://www.remotion.dev/docs/client-side-rendering)；[Remotion MCP](https://www.remotion.dev/docs/ai/mcp)）。

Remotion 的成熟度主要体现在分布式渲染上。Lambda 能把一条视频切给最多 200 个函数并行渲染，官方成本示例是 **1 分钟视频 $0.017、10 分钟远程 HD 视频 $0.103**（只含 Lambda 计算费），并明确提醒“视频里嵌视频”和 4K 都会显著推高成本（[Lambda 成本示例](https://www.remotion.dev/docs/lambda/cost-example)；[并发](https://www.remotion.dev/docs/lambda/concurrency)）。代价在授权：Remotion 是源码可见软件而非开源软件，**个人和 3 人以内的公司免费**，超过就要买公司许可，自动化流水线和 SaaS 归入“Automators”档，**每次成功渲染 $0.01，每月最低 $100**（[LICENSE](https://github.com/remotion-dev/remotion/blob/main/LICENSE.md)；[remotion.pro](https://www.remotion.pro/license)）。许可 FAQ 明确允许“用 AI 生成 Remotion 代码再渲染”的服务，但禁止让用户上传自己的 Remotion 工程来渲染（[License FAQ](https://www.remotion.dev/docs/license/faq)）。尚未合并的 5.0 草案还会把外包人员计入人数，并要求 Automators 用户必须设置 license key、开启遥测（[PR #3750](https://github.com/remotion-dev/remotion/pull/3750)；[Telemetry](https://www.remotion.dev/docs/telemetry)）。

HyperFrames 是 HeyGen 以 **Apache-2.0** 发布的框架，口号是“写 HTML、渲染视频、为 agent 而建”。一个合成就是一个 HTML 文件，元素上带 `data-start`、`data-duration`、`data-track-index` 等时间属性；动画用 GSAP、CSS、WAAPI 或 Lottie，先暂停，再按帧 seek。它不需要构建，自带 7 个 skill 和约 450 个现成区块（[README](https://github.com/heygen-com/hyperframes/blob/main/README.md)）。关于它的发布时间和规模，笔记之间有冲突。编排调研引用的是聚合站的说法：“2026-03-10 或 04-17 开源、2.3 万或约 3.25 万星、v0.7.22、20 个 skill”（[yuv.ai](https://yuv.ai/blog/heygen-hyperframes-html-video)；[noqta](https://www.noqta.tn/en/blog/heygen-hyperframes-html-to-mp4-ai-agent-video-2026)）。框架调研则在 2026-10-27 直接查询了 npm 和 GitHub API，本报告以后者为准：**仓库创建于 2026-03-10，npm 0.1.0 发布于 2026-03-23；HeyGen 官方 X 帖的雪花 ID 解码后，公开发布日是 2026-04-16。截至 2026-10-27，项目有 73,664 星，最新版 0.8.208，累计 561 个版本**（[GitHub](https://github.com/heygen-com/hyperframes)；[npm](https://registry.npmjs.org/hyperframes)；[HeyGen on X](https://x.com/HeyGen/status/2044827454460871072)）。skill 数量以 README 写的 7 个为准。

也就是说，HyperFrames 的星数已经超过 Remotion，但项目只有约 6 个月历史，仍处于 0.x，一天发好几个版本。HeyGen 自己的对比页也承认 Remotion “更老、更成熟”，而 HyperFrames 的 Lambda 路径“更新”（[HF vs Remotion](https://hyperframes.heygen.com/guides/hyperframes-vs-remotion)）。changelog 里能看到“超过 16 核的主机上 H265 渲染失败”“宽 1080 的 SDR MP4 最右 8 列变黑”这类修复，正是年轻项目的典型信号（[Changelog](https://hyperframes.heygen.com/changelog)）。

两者谁更适合让 LLM 来写，现有证据互相矛盾。HeyGen 做过一次单次对比，同一个提示词、都用 Claude Code：HyperFrames 11 分 50 秒出片，Remotion 12 分 30 秒；Remotion 写了 1,037 行 TS、装了约 950 MB 依赖，HyperFrames 只写了 822 行 HTML（[HF vs Remotion](https://hyperframes.heygen.com/guides/hyperframes-vs-remotion)）。人人都是产品经理上一篇中文口播特效实测的结论正好相反：Remotion 用 7 分钟、$43 的 token 成本做完了约 1 分 24 秒的整条视频；HyperFrames 用了 14 分钟、花掉 $28 后半途停下，文字遮住人像，还因为本地缺 Google Fonts 导致中文乱码。不过作者给 HyperFrames 写了自定义 skill，却没给 Remotion 用 skill，条件并不对等（[woshipm](https://www.woshipm.com/ai/6408883.html)）。两次都是不受控的单次试验，唯一可靠的结论是：**必须用自己的素材做对照测试。**

中文内容和国内部署有几处共同的坑。最隐蔽的是字幕分词：Remotion 的 `createTikTokStyleCaptions()` 以空格切词，**中文字级 ASR 的输出没有空格，必须先自行分词，或在每个 token 前插一个空格，否则整段会挤在一页里**（[createTikTokStyleCaptions](https://www.remotion.dev/docs/captions/create-tiktok-style-captions)）。字体同样要自己负责：Remotion Lambda 只在 arm64 上内置 Noto Sans SC 等 CJK 字体（[Lambda runtime](https://www.remotion.dev/docs/lambda/runtime)）；HyperFrames 的转写已经修好了 CJK token 和字幕分组，但它在分布式渲染时禁用系统字体，字体必须随工程打包（[Changelog](https://hyperframes.heygen.com/changelog)；[Lint rules](https://hyperframes.heygen.com/reference/lint-rules)）。手机拍摄常见的 HEVC 不在 Remotion `<Video>` 的解码列表里，会自动回退到较慢的 `<OffthreadVideo>`（[Video tags](https://www.remotion.dev/docs/video-tags)），所以入库时统一转成 H.264 MP4 中间片是值得的。Remotion Lambda 只能跑在 AWS 上，两者都没有国内云的部署文档，面向国内用户时需要在阿里云或腾讯云的容器里自托管渲染器。隐私上也各有一处要注意：Remotion 浏览器端渲染**每次都会上报遥测，其中包括终端用户 IP**（[Telemetry](https://www.remotion.dev/docs/telemetry)）；HyperFrames 走 HeyGen 云渲染时，≥5 MB 的媒体会以**公开、未签名的 URL** 托管（[Cloud rendering](https://hyperframes.heygen.com/deploy/cloud)）。涉及未发布的创作者素材时，这两点都需要法务评估。

本报告的选型是 **Remotion 为主、HyperFrames 为辅、引擎可替换**，理由有三条。第一，本系统推荐的 LLM 用法是“预制组件库 + LLM 填 JSON 参数”，而不是让 LLM 自由写代码（见 LLM 一节）。Remotion 的强类型 `inputProps` 可以和时间线 IR 共用同一份 Zod schema，Player 预览和最终成片用同一套组件，所见即所得；HyperFrames 的 HTML 结构扁平，编辑落在属性层面（“Move → `data-start`”“Trim → `data-duration`”），更适合让 agent 快速产出一次性动效或研发新模板（[Editing existing videos](https://hyperframes.heygen.com/prompting/editing-existing-videos)）。第二，与本产品最接近的几家商业产品都跑在 Remotion 上：Submagic 上线 3 个月 ARR 达到 100 万美元，Crayo 月收入超过 50 万美元，还有 Revid。这是负载类型匹配的直接证据，只是这些数据来自 Remotion 自己的营销页（[Success Stories](https://www.remotion.dev/success-stories)）。第三，规模上来后授权费也不是决定因素：即使每月渲染 5 万次，费用也只有约 $500（测算），远低于人工复核成本，3 人以内的团队更是完全免费。反过来，如果团队预计会长期超过 3 人、需要“零遥测”的承诺，或者评测显示 HyperFrames 在自家素材上明显更好，可以把主引擎切过去，前提是 IR 不绑定任何一家。browser-use 的 video-use（29,945 星）和 OpenMontage 都已同时支持两个引擎，可见“引擎无关的 EDL/时间线 + 多个渲染后端”已经是 agent 视频工具的主流做法（[video-use](https://github.com/browser-use/video-use)；[OpenMontage](https://github.com/calesthio/OpenMontage)）。

### 其他框架与云 API 只适合做零件或备选

开源代码框架里，没有比这两者更稳的地基。Revideo（MIT）是唯一仍在发版、支持并行渲染的代码优先替代品，但背后的 Midrender 在 YC 登记的团队规模只有 1 人（[Revideo](https://github.com/midrender/revideo)；[YC](https://www.ycombinator.com/companies/midrender)）。Motion Canvas 自 2024-12 起没有新的 npm 版本，editly 停在 2022-12（[Motion Canvas npm](https://www.npmjs.com/package/@motion-canvas/core)；[editly npm](https://www.npmjs.com/package/editly)）。Twick 采用 Sustainable Use License，未经协议禁止做成托管服务或 SaaS；Etro 是 GPL-3.0（[Twick LICENSE](https://raw.githubusercontent.com/ncounterspecialist/twick/main/LICENSE.md)；[Etro](https://github.com/etro-js/etro)）。OpenCut 虽有 96,474 星，但正在从头重写，编辑器 API、MCP 和无头批量渲染都还只是计划（[OpenCut](https://raw.githubusercontent.com/OpenCut-app/OpenCut/main/README.md)）。

口播素材的解码、切割、缩放、叠加和编码，最适合交给原生管线。ffmpeg-python 自 2019 年起就没发过版，应改用 typed-ffmpeg（4.6.2，2026-10-21）；PyAV 很活跃；MLT 7.42 带来了基于 libplacebo 的 GPU 模块和 FFmpeg 9 支持，它的 XML 时间线还能直接用 Shotcut 打开（[typed-ffmpeg](https://github.com/lucemia/typed-ffmpeg)；[PyAV](https://github.com/PyAV-Org/PyAV)；[MLT releases](https://github.com/mltframework/mlt/releases)）。浏览器端的 ffmpeg.wasm 只有原生速度的 0.04–0.08 倍（[ffmpeg.wasm](https://ffmpegwasm.netlify.app/docs/performance)）。云 API 里，阿里云 IMS 的 Timeline JSON 和口播需求几乎一一对应：主轨用 In/Out 剪切，上层轨用 X/Y/Width/Height 做画中画，SubtitleTracks 放花字，还内置 AI_ASR、AI_TTS 和 AI_Avatar。官方计费页上 **1080P 合成 ¥0.06/分钟**（[IMS Timeline](https://help.aliyun.com/en/ims/developer-reference/timeline-configuration-description)；[IMS 计费](https://help.aliyun.com/zh/ims/video-clip)）。Shotstack 收费 $0.05–0.20/分钟，并提供 agent 约定文档和 `llms-full.txt`（[Shotstack pricing](https://shotstack.io/pricing/)；[agent conventions](https://shotstack.io/docs/guide/agents/conventions/)）。腾讯 MPS EditMedia 和火山 VOD 直接剪辑也接受 JSON 时间线，但查不到公开价格（[Tencent EditMedia](https://cloud.tencent.com/document/api/862/43010)；[BytePlus](https://docs.byteplus.com/zh-CN/docs/byteplus-vod/reference-submitdirectedittaskasync)）。

## 口播自动剪辑：字级时间戳决定剪辑质量的上限

### ASR：Qwen3 与 Paraformer 已取代 Whisper

到 2026 年底，中文 ASR 的开源第一梯队是阿里的 Qwen3-ASR 和小红书的 FireRedASR2。**Qwen3-ASR 于 2026-01-29 开源（Apache-2.0），1.7B 版在 AISHELL-2 上的 WER 为 2.71，略好于豆包 ASR 的 2.85**；在极端噪声普通话上是 16.17，而 Whisper-large-v3 是 63.17（[Qwen3-ASR GitHub](https://github.com/QwenLM/Qwen3-ASR)；[技术报告](https://arxiv.org/html/2601.21337)）。对剪辑更关键的是配套的 Qwen3-ForcedAligner：**它的中文平均对齐误差是 33.1 ms，NFA 是 109.8 ms；在 300 秒拼接音频上为 52.9 ms，WhisperX 则漂到 2,708 ms**。它的限制是单次最长只能处理 5 分钟音频，而且流式模式不输出时间戳（[Qwen3-ASR GitHub](https://github.com/QwenLM/Qwen3-ASR)）。FireRedASR2-LLM 在自家统计的 4 个普通话测试集上平均 CER 为 2.89，好于豆包的 3.69 和 Qwen3-ASR 的 3.76，但单段音频上限 40 秒，模型卡也没提时间戳（[HF: FireRedASR2-LLM](https://huggingface.co/FireRedTeam/FireRedASR2-LLM)）。这些都是厂商自报数字；第三方的 GigaSpeechBench 显示，Qwen3-ASR-1.7B 在多数中文领域子集上错误率最低（[arXiv 2606.28884](https://arxiv.org/pdf/2606.28884)）。FunASR 的 Paraformer-large 仍是务实之选：原生字级时间戳、支持热词、速度快（[FunASR 论文](https://arxiv.org/abs/2305.11013v1)）。

Whisper-large-v3 在工业测试集上的平均 WER 是 33.39，约为 Fun-ASR-Nano（16.72）的两倍（[Fun-ASR-Nano](https://huggingface.co/FunAudioLLM/Fun-ASR-Nano-2512/blob/main/README_zh.md)）；19k 星的 VideoLingo 也已经把默认引擎从 WhisperX 换成了 Qwen3-ASR + ForcedAligner（[VideoLingo](https://github.com/Huanshere/VideoLingo)）。**2023–2024 年那批以 Whisper 为核心的中文剪辑教程应视为过时。** 云端 ASR 的成本基本可以忽略。**百炼 paraformer-v2 为 0.00008 元/秒，约合 0.29 元/小时（测算）；qwen3-asr-flash-filetrans 为 0.00022 元/秒，开启 `enable_words` 后才返回字级时间戳，同步版 qwen3-asr-flash 则不返回**（[百炼录音文件识别](https://help.aliyun.com/zh/model-studio/recording-file-recognition)；[filetrans](https://help.aliyun.com/zh/model-studio/qwen3-asr-flash-filetrans)）。火山豆包录音文件识别极速版一次请求就返回逐字 `words` 数组，并带 `enable_ddc`（顺滑）开关，适合交互式剪辑（[火山引擎文档](https://docs.volcengine.com/docs/6561/1631584?lang=zh)），上下文里还能直传最多 5,000 个热词（[火山引擎](https://www.volcengine.com/docs/6492/2172368)）。建议 MVP 阶段用云端的 filetrans 或极速版，量起来以后自托管 Qwen3-ASR + ForcedAligner；剪辑链路一律走离线文件转写，不用流式。

### 去气口与 NG：规则先行，LLM 只判语义，删前保后

去气口和 NG 的行业做法已经很成熟：字级 ASR → 规则加 LLM 标出删除候选 → 按风险分级审核 → 按时间段物理切割 → 对剪后的成片重新转写生成字幕。剪映的“智能剪口播”、度加的“快速剪辑”，以及 Descript 的 Remove Retakes 和 Remove Filler Words 都是这个形态（[36氪](https://eu.36kr.com/zh/p/3973186277011715)；[度加剪辑](https://apps.apple.com/app/id1552875358)；[Descript changelog](https://feedback.descript.com/changelog/descript-season-6-release-version-91)）。公开规则里最具体的是开源 skill videocut v3。它把口误分成三类，统一按“删前保后”处理：句间重复指相邻或隔一句、开头共享 ≥5 个字，删掉前一句；句内重复是“A + 中间内容 + A”的模式，只删前一段；残句是说到一半停顿后重说，删掉残片。其他规则还有：**静音 ≥0.2 秒自动勾选删除，≥0.5 秒视为断句，最后一个字之后多出 0.3 秒以上的部分补删**。整句删除和长重复交给一个“对抗式审核 agent”复核，切割用 FFmpeg 的 `filter_complex` 做帧精确的 trim+concat，并按源视频参数重编码（[smithery: videocut](https://smithery.ai/skills/aiskillstore/videocut)）。

纯音量阈值的 auto-editor 仍是静音粗剪的基线（默认阈值 0.04，保留段前后各加 0.2 秒），但处理不了语义上的重复（[auto-editor](https://github.com/WyattBlue/auto-editor)）。Silero VAD 在单个 CPU 线程上处理一个 30 ms 的音频块不到 1 ms，可以放心对全部素材跑一遍（[silero-vad](https://github.com/snakers4/silero-vad)）。“那个”“就是”这类词有时有实际意思，应该让 LLM 结合上下文判断，或者交给人工确认。为避免跳切痕迹，本报告建议切点先对齐字边界再往外扩几十毫秒，每个切点加一段短交叉淡化（FFmpeg `acrossfade`/`afade`），句间保留约 0.2–0.4 秒气口。这些阈值是工程推断，需要在评测集上调；同机位的跳切，再用 punch-in 或 B-roll 盖住。

### 字幕：一屏一行十五字以内，纠错不许动时间轴

中文竖屏字幕的惯例是一屏一行、句末不加标点。Netflix 简体中文每行上限 16 字，开源剪口播字幕 skill 规定竖屏每行 ≤15 字，火山字幕接口推荐的分句长度也是 15（[Netflix](https://backlothelp.netflix.com/hc/en-us/articles/215274938-What-is-the-maximum-number-of-characters-per-line-allowed-in-Timed-Text-assets)；[videocut-subtitle](https://smithery.ai/skills/zrt-ai-lab/videocut-subtitle)；[火山引擎](https://www.volcengine.com/docs/6561/80909)）。断句可以先按 ASR 标点和停顿切成语义句，超长的再在逗号处或字间间隙最大处拆开；LLM 只负责标“在哪断”，不改字。纠错的铁律是：**保留原时间轴，只修术语和同音错字，不得添加没说出口的内容**（[videocut](https://smithery.ai/skills/aiskillstore/videocut)）。口播常常有提词器文稿，先把文稿和 ASR 结果做序列对齐，只把有差异的地方交给 LLM，比让 LLM 自由改写更安全。热词最好在识别阶段就解决，SeACo-Paraformer 热词、百炼自定义热词、豆包 context 热词和 Qwen3-ASR 的 system prompt 上下文各有各的接口（[FunClip](https://github.com/modelscope/FunClip)；[百炼热词](https://help.aliyun.com/zh/model-studio/custom-hot-words/)）。卡拉 OK 式的逐字动画直接用字级时间戳驱动。剪掉片段以后时间会累积偏移，所以字幕应该引用 transcript 里的词 ID，由编译器按剪辑映射重新计算（见 IR 一节）。关键词高亮、emoji 和花字可以让 LLM 对每句输出 `{keywords, emphasis_level, emoji}`，同一份标注能同时驱动花字、画面放大和音效。

### 放大与重构图：人脸 5 fps 采样就够

智能竖屏重构图的成熟做法是低帧率人脸检测加时序平滑。一个开源 skill 用 MediaPipe 的 478 点人脸网格以 5 fps 采样，跟随正在说话的人，没人说话时回退到画面中最大的人脸（[wjs-reframing-video](https://clawhub.ai/jianshuo/skills/wjs-reframing-video)）；OpusClip 也提供 Auto Reframe API（[OpusClip blog](https://www.opus.pro/blog/auto-resize-video-api)）。自动推拉方面，Submagic 的 Magic Zoom 有 6 种风格，由 AI 根据转写稿和语音同步触发（[Submagic](https://www.submagic.co/de/features/auto-zooms)）。本报告建议（工程推断）在 LLM 标出的强调句起点做 1.0→1.15–1.3 倍放大，以人脸框中心为锚点；同机位跳切点交替使用两个景别，让跳切显得像有意为之。渲染层应对包裹视频的容器做 CSS 变换，而不是直接变换视频元素（[HyperFrames Video components](https://hyperframes.heygen.com/guides/video-components)）。

抠像换背景时，RVM 不需要辅助输入，RTX 3090 FP16 下 HD 可达 172 fps，但它是 GPL-3.0，而且 2021 年以后基本没再更新；质量最好的是 MatAnyone 2（CVPR 2026），需要提供首帧 mask（[RVM](https://github.com/PeterL1n/RobustVideoMatting)；[MatAnyone 2](https://openaccess.thecvf.com/content/CVPR2026/html/Yang_MatAnyone_2_Scaling_Video_Matting_via_a_Learned_Quality_Evaluator_CVPR_2026_paper.html)）。眼神校正目前只有 NVIDIA Maxine/Broadcast、Captions/Mirage、Sieve 等闭源或托管方案可用，开源方案还不成熟（[Sieve](https://sievedata.com/blog/eye-contact-correction-gaze-correction-api)；[Captions](https://captions.ai/help/docs/visual/eye-contact)）。

### B-roll：检索词质量与中文素材覆盖是瓶颈

B-roll 的主流实现是：LLM 从转写稿里挑出可视化的概念，生成英文检索词，调 Pexels 或 Pixabay 搜素材，再按字级时间戳插到对应句子上。MoneyPrinterTurbo 和 Submagic 都这么做，质量瓶颈在检索词和素材库的覆盖面（[MoneyPrinterTurbo 流程解析](https://deepseek.csdn.net/6a87860510ee7a33f29d4d4e.html)；[toolsforhumans](https://www.toolsforhumans.ai/ai-tools/submagic)）。**Pexels API 默认每小时 200 次、每月 20,000 次**，按条款展示署名可以申请无限额度（[Pexels API](https://www.pexels.com/api/documentation/?language=javascript)）。调用量大约是“句子数 × 检索词数”，默认额度只够做少量视频，量产必须加缓存或申请提额。候选素材可以用支持中文的 jina-clip-v2 对关键帧做语义重排（[arXiv 2412.08802](https://arxiv.org/html/2412.08802v2)）。中国街景、人物这类素材在 Pexels 上覆盖很弱，国内素材库又查不到开放 API，需要靠自有素材库或 AI 生成补足（[B站专栏](https://www.bilibili.com/read/cv50258223)）。放置规则建议 B-roll 落在句首后约 0.2–0.5 秒、持续 1.5–4 秒、口播音轨不中断，优先盖在跳切点上（工程推断）。

### 音频：保守降噪，统一 -14 LUFS 出母版

ASR 应该用原始音频或轻度降噪的音频。成片人声用保守的掩码类模型 DeepFilterNet3，它在可懂度和音质上都优于 RNNoise（[Sinergi](https://publikasi.mercubuana.ac.id/index.php/sinergi/article/view/21917)）。要避免生成式增强：Resemble Enhance 主观音质虽高，但**有篡改说话内容的倾向**（[arXiv 2603.02641](https://arxiv.org/pdf/2603.02641)）。BGM 用 FFmpeg 的 `sidechaincompress` 以人声为侧链自动闪避，混音后用 `loudnorm` 两遍法做响度标准化（[FFmpeg Filters](https://ffmpeg.org/ffmpeg-filters.html)）。响度目标上，YouTube 约 -14 LUFS / -1 dBTP，这一点有多方共识；B站个人实测约 -12 LUFS；TikTok/Reels 约 -13 LUFS，属于第三方经验值；**抖音、视频号、小红书都没有官方数据**（[editingtools.io](https://editingtools.io/loudness/)；[B站专栏](https://www.bilibili.com/opus/942558919908130865)；[OpusClip](https://opus.pro/blog/best-loudness-normalizers)）。统一按 -14 LUFS 出母版最稳妥，目标是 B站时可以调到 -12 到 -13。

长视频切片是同一条链路的延伸。OpusClip 的 Virality Score 由 hook、flow、value、trend 四项组成（[OpusClip help](https://help.opus.pro/docs/article/virality-score)），FunClip 则把转写稿和提示词交给 LLM 选段（[FunClip](https://github.com/modelscope/FunClip)）。在清理好的 transcript 上，用 LLM 按一份评分细则给候选窗口打分即可。

## 文案视频：TTS 真实时长回填分镜，视觉成本相差两个数量级

### 脚本与分镜：两段式 LLM，加严格 schema

文案视频的主流做法是两段式 LLM：先写口语化文案，再拆成结构化的分镜 JSON，靠结构化输出保证程序能解析。OpenMontage 把每条流水线固定为 research → proposal → script → scene plan → assets → edit → compose 七个阶段（[OpenMontage](https://github.com/calesthio/OpenMontage)；[Pinggy](https://pinggy.io/blog/openmontage_agentic_video_production/)）；LTX Studio 发现，把镜头类型、角度、运动拆成独立的 JSON 字段，比用一段散文描述更稳定（[LTX](https://ltx.studio/blog/json-prompting-for-video-image-generation)）。各家模型的结构化输出成熟度不同：**百炼 Qwen 支持 `json_schema` + `strict:true`；Claude 的结构化输出位于 `output_config.format`，要求对象设置 `additionalProperties:false`；DeepSeek 只有 `json_object` 模式，官方承认偶尔会返回空内容；火山方舟（豆包）的结构化输出仍是 beta，官方不建议用于生产**（[百炼结构化输出](https://docs.bailian.console.aliyun.com/zh/model-studio/qwen-structured-output)；[Claude Docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)；[DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode)；[火山方舟](https://www.volcengine.com/docs/82379/1958523)）。不管用哪家，都要在应用层用 Zod 或 Pydantic 校验，失败时带上错误信息重试。

分镜的最小字段集应包括场景 ID、旁白（用于 TTS 和字幕）、屏幕大字（常常和旁白不同）、画面类型（库存、AI 图、AI 视频、数字人、图表、模板）、中英双语检索词或生成提示词、模板 ID 和参数、转场以及 BGM 情绪。**时长不让 LLM 估，而是用 TTS 的实际音频时长回填。** 阿里云 IMS 的“脚本化自动成片”也是这个设计：`GeneratePreviewOnly=true` 时只生成 Timeline，不收费，真正合成时再按剪辑计费（[IMS 计费](https://help.aliyun.com/en/ims/one-key-into-a-piece)）。

### TTS：开源已低于真人错误率，许可证才是硬约束

中文 TTS 的开源第一梯队，错误率已经低于真人录音。**Fun-CosyVoice3 在 test-zh 上的 CER 为 1.21（RL 版 0.81），论文中真人录音基线是 1.26**；它采用 Apache-2.0，支持 18 种以上方言，可以用指令控制情感和语速（[CosyVoice GitHub](https://github.com/FunAudioLLM/CosyVoice)；[CosyVoice 3 论文](https://arxiv.org/pdf/2505.17589)）。Qwen3-TTS（2026-01-22 开源，Apache-2.0）提供 3 秒声音克隆和方言预置音色（[Gigazine](https://gigazine.net/gsc_news/en/20260123-qwen3-tts-family-opensource)）。许可证是选型的硬约束：IndexTTS-2.5 情感控制强，支持 0.5–2.0 倍时长控制，但用的是 bilibili 自定义许可，商用需要发邮件洽谈；Fish Audio S2 Pro 是研究许可；F5-TTS 的权重是 CC-BY-NC，不能商用（[index-tts](https://github.com/index-tts/index-tts)；[Fish Audio](https://fish.audio/fr/blog/what-we-mean-by-open-source-for-s2/)；[vantaige](https://vantaige.io/ai-tool/f5-tts)）。

云 API 里，**阿里云 CosyVoice v3.5-flash 只要 0.8 元/万字符，v3-plus（声音复刻）为 2 元/万字符**（[v3.5-flash](https://help.aliyun.com/zh/model-studio/cosyvoice-v3-5-flash)；[v3-plus](https://help.aliyun.com/zh/model-studio/cosyvoice-v3-plus)）；MiniMax speech-2.8 为 $60–100/百万字符，ElevenLabs 为 $0.05–0.10/千字符（[MiniMax](https://platform.minimax.io/docs/guides/pricing-paygo.md)；[ElevenLabs](https://elevenlabs.io/pricing/api)）。豆包语音合成 2.0 的官方单价没查到，一份未注明日期的价目表写的是“5 元/万字符”（第三方，[ai-bot.cn](https://ai-bot.cn/sites/22232.html)）。字幕同步方面，阿里云智能语音交互的 `enable_subtitle` 可以返回字级时间，但官方提醒返回的文本是按发音切分的，上屏必须用原文，而且这条说明是否适用于百炼 CosyVoice 尚未核实（[阿里云时间戳](https://help.aliyun.com/zh/isi/developer-reference/timestamp-feature)）。最稳的策略是**逐句合成，用每句的音频时长拼出句级时间轴**，需要逐字高亮时再用强制对齐器补出字级时间，这样也方便单独重新生成某一句。MoneyPrinterTurbo 等开源项目默认用 Edge TTS（[MoneyPrinterTurbo](https://github.com/harry0703/MoneyPrinterTurbo)），研究员推断它本质上是在调用微软 Edge 朗读功能的非官方接口，商业产品不宜依赖。

### 素材与 AI 生成：配比决定成本

视觉层是文案视频成本的主要变量。免费库存素材（Pexels/Pixabay）几乎零成本，但 Pixabay 的许可禁止把素材作为独立文件再分发（[freeapihub Pixabay](https://freeapihub.com/apis/pixabay-api)）。AI 生图里，Qwen-Image（Apache-2.0，20B）的中文文字渲染尤其强，能直接生成带中文的画面（[Qwen-Image](https://huggingface.co/Qwen/Qwen-Image)）；MiniMax image-01 官方 $0.0035/张，Seedream 4.5 约 $0.04/张（第三方，来自转售商博客）（[MiniMax](https://platform.minimax.io/docs/guides/pricing-paygo.md)；[Evolink](https://evolink.ai/en/blog/seedream-pricing-guide-2026)）。AI 视频的第一梯队是 Seedance 2.0、HappyHorse、Kling 3.0 和 Veo 3.1，Artificial Analysis 榜单上 Seedance 2.0 和 HappyHorse-1.0 同为 1,211 Elo（[AA](https://artificialanalysis.ai/video/leaderboard/text-to-video)）。价格差距很大：MiniMax H3-Lite 768P 官方 **$0.04/秒**，Vidu Q3-turbo 1080p 官方 $0.07/秒；**Seedance 2.0 约 1 元/秒、Seedance 2.0 Mini 约 0.5 元/秒、Kling 3.0 720p 约 $0.084/秒，这三个都来自第三方整理或估算**（[MiniMax](https://platform.minimax.io/docs/guides/pricing-paygo.md)；[Vidu](https://platform.vidu.com/docs/pricing)；[17173](https://news.17173.com/content/03052026/080543693.shtml)；[ai-indeed](https://www.ai-indeed.com/encyclopedia/23583.html)；[Atlas Cloud](https://www.atlascloud.ai/blog/guides/kling-ai-api-pricing)）。

**OpenAI 已于 2026-09-24 移除 Sora 2 的全部 API**，依赖它的旧教程已经失效（[Make](https://help.make.com/openai-sora-and-video-modules-deprecation-by-september-24-2026)）。能开源自托管的只有 Wan 2.2（Apache-2.0），它的 TI2V-5B 在 RTX 4090 上生成 5 秒 720P 视频，未优化时要将近 9 分钟，批量吞吐有限（[Wan2.2](https://github.com/Wan-Video/Wan2.2)）。静态图动画化可以用 DepthFlow 做 2.5D 视差，成本很低，但它是 AGPL-3.0（[DepthFlow](https://pypi.org/project/depthflow)）。素材和文案对不上是“文字成片”公认的痛点，剪映的图文成片就出过“讲人工智能却配猫图”的案例（[KOC](https://www.koc.com.tw/archives/513023)），所以候选素材应该再过一遍多模态模型做语义重排。推荐的画面配比是：以 AI 图加模板动效为主，少量 AI 视频只用在开头的钩子镜头。

### 数字人：主线复用真人授权分身

没有真人素材时，数字人通常只出现在画中画或片头片尾。开源方案中，硅基智能的 HeyGem/Duix-Avatar 用约 10 秒视频克隆形象和声音，Docker 部署（[Duix-Avatar](https://cdn.jsdelivr.net/gh/duixcom/duix-avatar@main/README.md)）。口型精度最高的是字节的 LatentSync，连 MuseTalk 的论文也承认它在 HDTF 上 LSE-C 最佳（[MuseTalk 论文](https://arxiv.org/pdf/2410.10122)）；它的 1.6 版约需 18 GB 显存，许可证说法互相冲突。MuseTalk 1.5 约需 8 GB 显存，面部区域固定为 256×256（单一来源，[Creeta](https://news.creeta.com/en/open-source-lip-sync-models-2026/)）。Wan2.2-S2V（Apache-2.0）和 OmniHuman 1.5 代表“图片 + 音频直接生成说话视频”的新路线（[Wan2.2](https://github.com/Wan-Video/Wan2.2)；[PiAPI](https://piapi.ai/es/blogs/omnihuman-1-5-api-guide)）。商用方面，HeyGen 的 API 计价各来源说法冲突，硅基、蝉镜、腾讯智影都查不到官方 API 单价（[Creatify](https://creatify.ai/blog/heygen-pricing-(2026)-plans-and-what-you-ll-actually-pay)）。对本产品最有价值的用法，是用口播作者本人授权的形象训练一个数字分身，批量生产文案视频。但这必须留存书面授权，而且每条视频都要做 AI 标识（见合规一节）。

### 模板与音乐：动效靠代码模板，BGM 靠自有曲库

图文类动效普遍采用“模板 + JSON 参数”。Creatomate 在可视化编辑器里把字段标为动态，再用 JSON 批量替换；Shotstack 则是 JSON 时间线。但 overshoot、stagger、手调缓动曲线这类效果很难用纯 JSON 表达（[Creatomate](https://creatomate.com/docs/fundamentals/getting-started/api-automation)；[Motionbox](https://motionbox.io/blog/best-json2video-alternatives-in-2026)），这正是代码模板（Remotion/HTML）的用武之地。建议内置一组模板，覆盖图文解说、文字快闪、Top N 列表、数据图表、金句卡、左右对比、时间线、新闻播报和商品卖点卡，由 LLM 在分镜里选 `template_id` 并填参数，逐字动画复用 TTS 时间戳。

音乐方面，MiniMax 付费音乐 API **自 2026-08-20 起不再向新用户开放**，Suno 没有官方按首计费的 API、只有转售，Mureka 有官方预付费 API（[MiniMax](https://platform.minimax.io/docs/guides/pricing-paygo.md)；[CostBench](https://costbench.com/software/ai-music-apis/suno-api/)；[CometAPI](https://www.cometapi.com/ai-music-api-pricing/)）。MoneyPrinterTurbo 自带的 BGM 来自 YouTube，它的 README 自己写着“如侵权请删除”（[MoneyPrinterTurbo](https://github.com/harry0703/MoneyPrinterTurbo)）。生产系统应该建立自有曲库，每首带情绪、BPM、时长标签和授权记录，AI 音乐只作补充。卡点（beat-sync）没找到现成方案，需要自建节拍检测。

## 统一时间线 IR：剪辑决策和帧级时间线分两层存

现有格式没有一种能同时满足三个要求：LLM 好写、渲染器能直接用、能交给 NLE 精修。OTIO 是嵌套很深的对象树，维护者明确建议用官方库读写、不要手写，它适合导出到 Resolve（18.5 及以上）和 Premiere（2024 年 10 月起进入 Beta），但跨 NLE 时特效和转场通常无法转换（[OTIO spec](https://jcmorin-opentimelineio.readthedocs.io/en/stable/tutorials/otio-file-format-specification.html)；[Resolve manual](https://www.steakunderwater.com/VFXPedia/__man/Resolve18-6/DaVinciResolve18_Manual_files/part1410.htm)；[Adobe Community](https://community.adobe.com/t5/premiere-pro-beta-discussions/now-in-beta-otio-import-and-export/m-p/14985932)；[KDE forum](https://forum.kde.org/viewtopic.php%3Ff=265&t=165060.html)）。Shotstack 用浮点秒表示 start 和 length（[Shotstack API](https://shotstack.io/docs/api/)）。阿里云 IMS Timeline 的文档里没有提到关键帧，也没有字级时间戳字段（[IMS Timeline](https://help.aliyun.com/en/ims/developer-reference/timeline-configuration-description)）。Remotion 官方推荐的编辑器数据模型是 `{from, durationInFrames, id}`，加上以 `type` 区分的判别联合（[Building a timeline](https://www.remotion.dev/docs/building-a-timeline)）。剪映草稿则版本兼容性不稳定。务实的做法是自定义一份带版本号的标准 IR，再写适配器导出到各个目标。

设计上有五条原则，综合自编排调研的推断和上述几种格式。第一，**时间用整数帧加有理数 fps 表示**（如 30000/1001），与 Remotion 的 `from/durationInFrames` 和 MLT 的帧号一致，只在导出到 IMS 或 Shotstack 时才换算成秒，避免浮点数在 LLM、编辑器和渲染器之间来回传递时累积误差；transcript 可以保留 ASR 原生的毫秒，由编译器负责对齐到帧。第二，**分两层存**：决策层记录对 transcript 的引用式编辑操作，包括删哪个词区间、为什么删、谁删的、置信度多少、有没有被人锁定；时间线层存编译出来的帧精确 clip，即 `sourceIn/sourceOut` 加 `timelineStart`，分别对应 IMS 的 In/Out/TimelineIn 和 OTIO 的 source_range。这样撤销、解释和人工复核都有据可查。第三，**字幕不写死成 SRT，而是引用词 ID**，剪辑之后由编译器按映射重新计算时间，导出时再生成 SRT 或 ASS。第四，**特效、转场和关键帧用判别联合表示**，只暴露少量可移植的类型，各家私有的效果放进 `vendorExtensions`。第五，**顶层带 `schemaVersion` 和 `generator`**（模型和提示词版本），每次升级都写迁移函数；schema 只用 Zod 定义一次，再经 zod-to-json-schema 同时提供给 Remotion props、前端编辑器、Python 端的 Pydantic 和 LLM 结构化输出。下面是一份示意，字段是本报告的建议，不是现成标准。

两类视频的“时间基准”正好相反：口播以真人语音为准，剪辑是对 transcript 做减法；文案视频以 TTS 为准，画面去适配声音。正因为如此，时间线必须由编译器生成，而不是让 LLM 直接写。

| 编译目标 | 用途 | 映射要点 | 主要风险 |
|---|---|---|---|
| Remotion `inputProps` | 浏览器预览与主渲染 | 每条轨道对应 `<Sequence>`；clip 的 `timelineStart`/时长直接对应 `from`/`durationInFrames` | 授权费；HEVC 素材回退到慢路径 |
| HyperFrames HTML | agent 研发的动效片段 | clip 对应 `data-start`/`data-duration`/`data-track-index`，裁片头对应 `data-media-start` | 0.x 版本变动快 |
| FFmpeg 滤镜图 | 纯剪切快速路径、音频处理 | cuts 编译成 `trim`/`atrim` + `concat`，配合 `acrossfade`、`sidechaincompress`、`loudnorm` | 与预览不是同一套实现 |
| 阿里云 IMS Timeline | 国内托管渲染 | 主轨对应 `In/Out/TimelineIn`，叠加轨对应 `X/Y/Width/Height`，字幕导出为 SRT/ASS | 以秒为单位；文档没有关键帧 |
| 剪映草稿 | 人工精修 | 通过 pyJianYingDraft 写入片段、关键帧和文本，字幕只能以 SRT 导入 | 版本兼容；没有官方 API |

## LLM 当剪辑师：只引用词 ID，不输出时间戳

研究原型和商业产品已经收敛到同一个模式：先把媒体转成文本，LLM 在一组受限的工具里做规划并通过 ID 引用素材，每一步都可以审批或回退，最后由确定性的渲染器执行。LAVE（IUI 2024）给每段素材分配一个数字 ID，agent 先输出“GOAL + ACTIONS”形式的计划，用户逐个批准后才转成函数调用；它的剪辑精度只有 1 秒，分镜理由也会出现幻觉（[LAVE](https://arxiv.org/html/2402.10294v1)）。Descript Underlord 通过编辑转写文本来剪视频，每次编辑的结果都可以接受或拒绝（[Descript blog](https://www.descript.com/blog/article/underlord-ai-video-editor-primer)）。Shotstack 的厂商文章把原则讲得最直白：“LLM 只决定做什么”，渲染交给带时间码的 JSON 时间线，并承认“大多数管线对输出是盲的”（[Shotstack](https://shotstack.io/learn/how-an-agentic-video-editing-pipeline-works/)）。需要注意，Shotstack 卖的正是它推荐的那个渲染层。

落到口播上，推荐的分工分四层。最底层是确定性规则，直接处理静音、气口、高置信度的口癖词和超过阈值的停顿压缩。LLM 只做需要语义判断的事：重复和 NG 段（选最后一遍或最流畅的一遍）、跑题段、重点句（用于花字、放大、B-roll），以及标题、封面文案和章节。LLM 输出的不是时间戳，而是对 transcript 的引用式操作，例如 `{"op":"delete","fromWord":"w_0412","toWord":"w_0437","reason":"retake"}`，再由编译器转成帧精确的切点，补上 padding 并对齐到零交叉点。最后一层是校验：用结构化输出或工具调用配合 Zod 校验，失败时把校验错误回传给模型重试。这和 LAVE 用数字 ID 引用片段、Descript“文本即时间线”是同一个思路，能避免浮点时间戳带来的幻觉和误差。videocut v3 的做法也值得借鉴：每类口误由一个 agent 检测，高风险删除再交给对抗式审核 agent（[videocut](https://smithery.ai/skills/aiskillstore/videocut)）。人工改过的操作带 `origin:"user"` 并加锁，LLM 重跑时必须把它们当作约束，否则会出现“AI 把人改过的地方又改回去”的体验问题。

上下文长度不是问题。按每分钟 200–300 字的常见语速估算（研究员推断），5 分钟中文口播约 1,000–1,500 字，带上词 ID 也只有几千 token；DeepSeek 的 `deepseek-flash` 和百炼的 qwen3.8-flash 都支持 1M 上下文（[DeepSeek 定价](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)；[百炼模型价格](https://help.aliyun.com/zh/model-studio/model-pricing)），因此不需要分块。不要把逐字时间戳 JSON 原样塞进提示词，应压缩成 `[w_0412]那个 [w_0413]我们` 这样的行内 ID 格式。只有 30–60 分钟以上的长素材，才需要先做章节摘要再按 map-reduce 方式处理。价格上，`deepseek-flash` 高峰时段输入 2 元/百万 token、输出 8 元/百万 token，闲时减半；qwen3.8-flash 输入 0.8 元、输出 2.7 元（[DeepSeek 定价](https://api-docs.deepseek.com/zh-cn/quick_start/pricing)；[百炼模型价格](https://help.aliyun.com/zh/model-studio/model-pricing)）。建议剪辑决策优先用 strict schema 最成熟的百炼 Qwen；DeepSeek 更便宜，但必须自己做校验；创意文案可以交给 Claude 或 GPT。

**剪辑决策用 JSON，代码生成只用于研发模板。** Remotion 的许可允许“由 AI 生成代码再渲染”的 SaaS，也允许终端用户编辑由服务生成的代码，但不允许用户上传自己的代码（[License FAQ](https://www.remotion.dev/docs/license/faq)）。Remotion 还给出了在浏览器里即时编译 LLM 生成的 TSX 的方案（[JIT](https://www.remotion.dev/docs/ai/dynamic-compilation)），HyperFrames 的 linter 则专门拦截 agent 常犯的错误，例如用 GSAP 动画布局属性、字体缺少 `@font-face` 声明（[Lint rules](https://hyperframes.heygen.com/reference/lint-rules)）。即便如此，线上生产仍应走“预制组件 + LLM 填参数”，代码生成限定在离线环境，由工程师审核后才入库成为新模板。

最后是视觉自检闭环。已有论文验证过“渲染 → VLM 审查 → 改代码”的流程：PhysicsSolutionAgent 先渲染出视频，让 VLM 检查元素重叠、文字可读性和内容被裁切等问题，再把批评转成提示词交给编码 agent 修改 Manim 代码（[arXiv 2601.13453](https://arxiv.org/pdf/2601.13453)）；LumiVideo 的调色 agent 最多迭代 5 轮（[arXiv 2604.02409](https://arxiv.org/pdf/2604.02409)）；video-use 的流水线里也有 Self-Eval 一步（[video-use](https://github.com/browser-use/video-use)）。对口播最有价值的检查项有四个：字幕是否落入平台 UI 的遮挡区，花字是否压住人脸，有没有黑帧或跳帧，开头是否带了显式 AI 标识。实现时先做几何检查，用安全区矩形和文本包围盒直接计算，比 VLM 更便宜也更可靠。但没有任何平台公布过非广告内容的安全区，第三方经验是把字幕放在 Y=1200–1550 一带（[visu.network](https://visu.network/tools/safe-zone-checker/)；[blitzcut](https://blitzcutai.com/blog/best-caption-placement-short-form-video)），因此安全区要做成可配置的预设。几何检查之后，再对低分辨率预览抽帧，交给 VLM 按清单打分，并设置最大迭代次数。

## 编排与渲染：先用 Postgres 加队列，人审等待变长后再上 Temporal

一条完整的作业是一个 DAG：

```
ingest → [proxy ‖ audio] → asr → rules_cut → llm_decide → compile → human_review → render → qc → aigc_label → publish
```

它运行时间长、容易失败，中间还要等人审核，适合 durable execution。建议每一步都写成纯函数形式 `artifact = f(inputs, params, version)`，缓存键取 `sha256(源文件) + 步骤名 + 步骤版本 + hash(参数)`，产物写入对象存储并在 Postgres 中登记（研究员推断）。ASR 结果、代理文件、波形、抽帧和 VLM 描述最值得缓存；LLM 决策按 `prompt_version + model` 缓存，方便做 A/B 测试和回放。1–5 人团队起步，用 Postgres 任务表加一个队列就够了：TS 技术栈用 BullMQ，Python 用 Celery 或 Dramatiq，也可以用托管的 Trigger.dev。Trigger.dev 的官方示例正好是用 FFmpeg 处理视频，并且在长生命周期容器里运行代码（[Trigger.dev](https://trigger.dev)）；Inngest 则是通过 HTTP 调用你的 serverless 端点，每一步受约 15 分钟的执行时长限制（第三方说法，[openalternative](https://openalternative.co/trigger)）。用 BullMQ 时，`human_review` 需要拆成“两个独立 job + 数据库状态机”。

等人审等待变成几小时甚至几天，再迁移到 Temporal。迁移时要注意：Activity 必须设置 Start-To-Close 超时，否则 Worker 崩溃后 Server 察觉不到；心跳可以携带进度，重试时从断点续跑；**取消信号只在心跳时送达，所以长时间运行的 FFmpeg 和渲染 Activity 必须定期发心跳**（[Temporal](https://docs.temporal.io/encyclopedia/detecting-activity-failures)）。队列建议按资源分层为 `cpu-light`（探测、LLM 调用）、`cpu-heavy`（FFmpeg）、`gpu`（自托管 ASR/TTS/抠像）和 `render`（Chromium 渲染），每层设独立的并发上限，并按租户做公平调度。MoneyPrinterTurbo 的批量任务是顺序执行的，上限 100 个，可以作为反面参照（[MoneyPrinterTurbo](https://github.com/harry0703/MoneyPrinterTurbo)）。扩缩容可以用 KEDA 的 ScaledJob，它为每个事件创建一个 Kubernetes Job，默认每 30 秒轮询一次触发器；注意**更新 ScaledJob 时默认会终止正在运行的 Job**，会打断进行中的渲染，需要改用合适的发布策略（[KEDA](https://github.com/kedacore/keda-docs/blob/main/content/docs/2.12/concepts/scaling-jobs.md)）。进度上报方面，FFmpeg 用 `-progress pipe:1`，Remotion 用 `onProgress` 回调，写入 Redis 后通过 SSE 推给前端。

媒体基础设施沿用经典的“代理编辑、原片渲染”模式。浏览器用 STS 临时凭证分片直传 OSS；入库时生成两份文件，一份 H.264 中间片让 Remotion 走快路径，一份 540p/720p 代理，GOP 设为每秒一个关键帧以便浏览器拖动定位，另外再生成波形 JSON 和缩略图雪碧图。只要代理保留原片的帧率和时间基，IR 里的 `sourceIn/sourceOut` 对两者同样有效。5 分钟口播单机渲染就够了，分片只在批量出片或长视频时才值得做。自建分片时，按场景边界切块并对齐 GOP，用 concat demuxer 拼接，音频整轨单独渲染后再 mux，避免块边界出现爆音。

国内部署要绕开两个限制：Remotion Lambda 只能用在 AWS 上，Cloud Run 版处于 alpha 且没有在积极开发（[Cloud Run status](https://www.remotion.dev/docs/cloudrun/status)）。因此国内需要在容器里自托管 Remotion 渲染器（它没有内置分布式），或者用 HyperFrames 的 Docker 渲染，后者会锁定 Chromium、字体集和 FFmpeg 编码器的版本（[Determinism](https://hyperframes.heygen.com/concepts/determinism)）。自托管模型可以用按秒计费的 GPU：Modal 的 T4 为 $0.59/小时、L4 为 $0.80/小时（[Modal](https://modal.com/pricing)）；阿里云函数计算 3.0 按配置规格乘时长计费，但 CU 与人民币的换算价没有查到（[FC 3.0](https://help.aliyun.com/zh/functioncompute/fc-3-0/product-overview/billing-overview-1)）。

GPU 编码只对原生管线有意义。NVIDIA 官方数据中，单个 NVENC 引擎在 Ada 架构上编码 1080p H.264，P5 预设为 283–291 fps，P1 为 885–910 fps（[NVENC App Note](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-application-note/index.html)）；PyTorch 的基准测试中，8 线程软件编码约 76 fps，NVENC 从主机内存取帧约 167–215 fps，帧已在 GPU 上时约 371 fps（[PyTorch](https://pytorch.org/audio/main/tutorials/nvenc_tutorial.html)）。关于消费级显卡的并发会话上限，笔记里出现了 3、5、8、12 四种说法。**本报告以 NVIDIA 官方 Video Codec SDK 13.0 文档为准：GeForce 等非认证显卡，整个系统最多 8 个并发编码会话；数据中心卡和专业卡只受资源限制**（[NVENC App Note](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-application-note/index.html)）。8 路上限需要较新的驱动（Windows ≥551.76、Linux ≥550.54.14），这一点来自论坛转引的 SDK 12.2 说明（[NVIDIA forum](https://forums.developer.nvidia.com/t/how-to-increase-number-of-nvenc-concurrent-sessions/169367)）。3 路和 5 路是旧驱动时代的限制，已被取代（[Tom's Hardware](https://tomshardware.com/news/nvidia-increases-concurrent-nvenc-sessions-on-consumer-gpus)；[Guru3D](https://www.guru3d.com/news-story/nvidia-removes-encoding-limitations-on-consumer-gpus-allowing-up-to-5-simultaneous-streams.html)）；Wikipedia 写的 12 路没有和 NVIDIA 文档核对过（[Wikipedia](https://en.wikipedia.org/wiki/NVENC)）；Livepeer 说的“2–3 路后降速或报错”描述的是实际性能退化，不是硬上限（[Livepeer](https://docs.livepeer.org/v2/resources/references/go-livepeer/gpu-support)）。结论是：生产环境的转码集群用 L4、T4、A10 这类数据中心卡就能绕开这个问题；如果用消费卡，要在实际的驱动版本上做压力测试。

浏览器引擎的瓶颈在逐帧截图，GPU 编码帮不上多少忙。HyperFrames 文档里，300 帧的 1080p 合成仅因一条 CSS 声明，渲染时间就从 9.8 秒变成 25 秒（[Performance guide](https://hyperframes.heygen.com/guides/performance)）；Remotion 也提醒，blur、阴影、渐变这类依赖 GPU 的 CSS，在没有 GPU 的云主机上很慢（[Performance](https://www.remotion.dev/docs/performance)）。因此模板设计规范里要明确禁止大面积的 `filter: blur()` 和 `backdrop-filter`。

## 人工微调与导出剪映：草稿是交接件，不是渲染器

降低人工成本的关键在编辑器 UX。建议左侧放 transcript 视图，AI 删掉的词用删除线显示并按原因（静音、口癖、NG、跑题）着色，一键可恢复；右侧放 Player 预览；下方是简化时间线，包含主轨和花字、B-roll、BGM、字幕几条轨。每个 AI 决策都带 `reason` 和 `confidence`，低置信度的进入“待确认”队列，这样人只需要复核少数片段，不必把整片重看一遍。研究也支持这种设计：ExpressEdit 会向用户展示指令的每一部分是如何被理解的，用户可以逐项调整（[ExpressEdit](https://arxiv.org/html/2403.17693v1)）；LAVE 提醒 LLM 的建议可能让创意变窄，主张辅助功能应该可以开关（[LAVE](https://arxiv.org/html/2402.10294v1)）。Brand Kit 要把 style 和 content 分开存，字体、配色、字幕样式、片头片尾、LOGO 位置和各平台的安全区预设都放在 style 里，批量生产就是“同一模板 × 多份素材”。

预览用 Remotion Player 读同一份 IR，可以保证所见即所得。但使用 Player 按许可条款也算“自动化”用途，官方的 `<Timeline>` 组件和 Editor Starter 都要付费，时间线也可以按文档自建（[Timeline](https://www.remotion.dev/docs/timeline)；[Editor Starter](https://www.remotion.dev/docs/editor-starter)；[Building a timeline](https://www.remotion.dev/docs/building-a-timeline)）。如果最终渲染走 FFmpeg 或 IMS，就要维护两套实现，容易出现预览和成片不一致，这是选型时要权衡的一点。浏览器端的另一个选择是 WebAV，它有中文文档，但自 2026-01 起没有再更新（[WebAV](https://github.com/WebAV-Tech/WebAV)）。

剪映草稿是国内创作者最常用的精修出口。pyJianYingDraft（Apache-2.0，4,700 星，0.3.1 发布于 2026-10-14）支持片段裁剪与变速、关键帧、蒙版、特效转场、富文本和模板替换，但字幕只能以 SRT 导入；功能表标注支持剪映 5.9 和 10.8；Linux 和 macOS 只能生成草稿；**批量导出只能在 Windows 上的剪映 ≤6.8 中进行**，要靠 uiautomation 接管鼠标和窗口，还需要 VIP 导出权限（[pyJianYingDraft](https://github.com/GuanYixuan/pyJianYingDraft)）。capcut-mate 把草稿生成包装成 REST/OpenAPI 接口，可以导入 Coze、接入 n8n，但它的 `gen_video` 能否自托管，README 说得不清楚（[capcut-mate](https://github.com/Hommy-master/capcut-mate)）。VectCutAPI 同时提供 HTTP 和 MCP 接口，带 `jianying_pro_10` 草稿配置，但云渲染模块不开源（[VectCutAPI](https://github.com/sun-guannan/VectCutAPI)）。

关于新版剪映是否加密 `draft_content.json`，两份资料说法冲突。JianYingDraft.PY 称剪映 6 以上做了加密，只支持 5.9 及以下（[PyPI](https://pypi.org/project/JianYingDraft.PY/1.0.2)）。pyJianYingDraft 则说能生成 10.8 版本的草稿，同时承认新版的 `draft_content.json` “往往不是明文可读的”，模板模式需要自定义 `fallback_loader`（[pyJianYingDraft](https://github.com/GuanYixuan/pyJianYingDraft)）。本报告的理解是：**加密或混淆影响的是“读取”新版剪映保存的草稿**，也就是模板模式这类“读-改-写”操作；**“生成”一份新的明文草稿再让新版剪映打开，目前仍有项目报告可用**，pyJianYingDraft 的 10.8 支持和 VectCutAPI 的 `jianying_pro_10` 配置都是例证。JianYingDraft.PY 的说法更可能反映它自身实现的局限，这一点是推断；加密从哪个版本开始，目前没有权威说明，字节的服务条款也未调研。

由此得出的设计是：系统只生成草稿，不回读用户的剪映工程；固定几个已测试的剪映版本做回归测试；把剪映导出定位为“尽力而为”的交接件，不拿剪映当渲染引擎。剪映里做的修改不会回流到 IR，这一点要坦然接受；需要让人工修改反哺 AI 的，放在自家编辑器里完成。专业 NLE 方面，OTIO 可以导入 Resolve（18.5 及以上）和 Premiere（Beta），auto-editor 能导出 Premiere、Resolve 和 FCP 的 XML，阿里云 IMS 也能把工程导出为 Premiere 格式（按剪辑计费）（[auto-editor](https://github.com/WyattBlue/auto-editor)；[IMS 计费](https://help.aliyun.com/zh/ims/video-clip)）。另外，Resolve 的外部脚本只有付费的 Studio 版才支持（[Arch Wiki](https://wiki.archlinux.org/title/Davinci)）。

| 混合型（推荐） | 12 张 AI 图 + 一个 5 秒 AI 视频钩子：MiniMax H3-Lite $0.04/秒（官方）至 Seedance 2.0 约 1 元/秒（第三方） | 1.7–8.4 | ≈1.9–8.6 |
| 全 AI 视频型 | 60 秒：MiniMax H3-Lite（官方）至 Seedance 2.0（第三方） | 17–60 | ≈17–60 |

其中固定的几项都很小：LLM 约 0.08 元，TTS 约 0.024 元（声音复刻音色约 0.06 元），渲染约 0.12 元（来源：[CosyVoice v3.5-flash](https://help.aliyun.com/zh/model-studio/cosyvoice-v3-5-flash)；[MiniMax](https://platform.minimax.io/docs/guides/pricing-paygo.md)；[Evolink](https://evolink.ai/en/blog/seedream-pricing-guide-2026)；[17173](https://news.17173.com/content/03052026/080543693.shtml)）。数字人和 BGM 的成本没有算进去：数字人 API 查不到官方单价，自托管则取决于吞吐。

两张表说明的是同一件事。ASR、LLM、VLM 加起来每条只要几毛钱，真正的成本杠杆有三个：一是画面配比，全 AI 视频比混合型贵一个数量级；二是渲染方式和存储生命周期，原片和代理文件应在 7–30 天后转入低频存储或删除，预览走 CDN，用户下载用带时效的签名 URL；三是人工复核分钟数，这一项远超云成本。Remotion 许可在规模上同样是小头，月渲染 5 万次约 $500，10 万次约 $1,000（测算）。海外的 JSON 渲染 API 则贵得多：按 1 美元 ≈ 7.1 元换算，Shotstack 的 $0.05–0.20/分钟是 IMS 1080P 价格的 6–25 倍（测算）（[Shotstack pricing](https://shotstack.io/pricing/)）。

## 合规与分发：生成内容双重标识，克隆声音单独同意

《人工智能生成合成内容标识办法》与强制性国家标准 GB 45438-2025 同步，自 **2025-09-01** 起施行（[新华网](https://www.news.cn/politics/20250314/b7a24028f2924b7681e6ed1bfbd8fade/c.html)）。办法第四条要求视频“在视频起始画面和视频播放周边的适当位置添加显著的提示标识”，音频要在适当位置加语音提示或节奏提示；第五条要求“在生成合成内容的文件元数据中添加隐式标识”，内容包括生成合成内容属性、服务提供者名称或编码以及内容编号；第九条允许在用户协议中明确用户义务后，向申请者提供不含显式标识的内容，但须“依法留存提供对象信息等相关日志不少于六个月”；第十条规定任何组织和个人不得恶意删除、篡改、伪造、隐匿标识，**也不得为此提供工具或服务**（[网信办原文](https://www.cac.gov.cn/2025-03/14/c_1743654684782215.htm)）。这意味着本系统不能提供“去 AI 水印”之类的功能。

隐式标识的技术格式方面，TC260 的视频元数据实践指南允许用原生结构或 XMP 命名空间写入，必选字段为 `Label`、`ContentProducer`、`ProduceID`、`ContentPropagator` 和 `PropagateID`（[Digital Policy Alert](https://digitalpolicyalert.org/event/33150-tc260-adopted-guidelines-on-identification-methods-for-ai-generated-synthetic-video-content)）。阿里云 SASE 提供了一个可参考的厂商实现：元数据通过 `XmpKvBase64` 以 `AIGC=` 为前缀传入，`Label=1` 表示 AI 生成（[阿里云 AIGC 视频标识](https://help.aliyun.com/zh/sase/getting-started/aigc-video-logo-add-guide)）。平台侧，抖音同日开始执行：创作者需要主动添加显式标识；没有标识但被平台检测为疑似 AI 的内容，会标注“疑似使用了AI生成技术”；元数据里已有服务提供者隐式标识的，会显示“作品含AI生成内容”（[IT之家](https://www.ithome.com/0/879/586.htm)；[澎湃](https://m.thepaper.cn/newsDetail_forward_31523045)）。另外，《互联网信息服务深度合成管理规定》第 12 条要求提供人脸、人声显著编辑功能时提示使用者取得被编辑者的单独同意，第 14 条要求合成人声要显著标识（[China Law Translate](https://www.chinalawtranslate.com/deep-synthesis/)）。

对本系统来说，文案视频里的 TTS、AI 画面和数字人都明确属于生成合成内容。只做剪切、字幕和调色的真人口播一般不算，但一旦用了 AI 配音、数字人、AI 换背景或 AI 扩图，就落入标识范围；这一判断是研究员推断，需要法务确认。落地上，IR 里的 `aigc` 字段由流水线根据实际用到的生成步骤自动置位，用户不能静默关闭隐式标识。渲染后按 TC260 字段写入元数据，`ProduceID` 与内部的 `render_id` 一一对应并入库，满足溯源要求。显式标识作为模板里一条不可删除的系统轨道（片头若干秒加角标）；用户选择去掉显式标识时，留存其协议同意记录和对象信息不少于六个月。克隆声音和训练数字分身之前，强制上传并存档本人的书面授权。GB 45438 对显式标识的量化要求（文字高度占比、持续时长）原文没有拿到，相关常见说法都未经核实，需要等法务拿到标准原文后再定参数。

分发方面，各平台差别很大。抖音有正式的开放平台 API：上传文件 ≤4 GB，超过 300 MB 必须分片，视频时长 ≤15 分钟，需要在控制台申请“代替用户发布内容到抖音”的能力，**同一用户在同一应用下每天最多发布 75 个作品**，API 页面上没有找到 AIGC 声明字段（[抖音上传视频](https://developer.open-douyin.com/docs/resource/zh-CN/dop/develop/openapi/video-management/douyin/create-video/upload-video)；[抖音创建视频](https://developer.open-douyin.com/docs/resource/zh-CN/dop/develop/openapi/video-management/douyin/create-video/video-create)）。视频号没有找到面向第三方的官方发布 API，现有方案都是用浏览器自动化操作视频号助手（[tessl](https://tessl.io/registry/skills/github/TeamWiseFlow/xiaobei/wechat-channels-publish)）；小红书的开源方案用的是非官方接口（[tessl: xhs-publish](https://tessl.io/registry/skills/github/TeamWiseFlow/xiaobei/xhs-publish)）；B站开放平台有投稿接口，但能找到的文档最后修改于 2022 年（[bilibili apifox](https://bilibili.apifox.cn/api-23706538)）。因此，自动发布只对抖音走官方 API，视频号和小红书做“一键下载 + 人工发布”。RPA 违反平台规则、有封号风险，不建议作为核心功能。

## 四阶段路线图：先跑通口播，再扩文案视频，最后规模化

| 阶段（时长为估计） | 交付物 | 关键技术选择 | 进入下一阶段的门槛 |
|---|---|---|---|
| 0：评测与选型（2–3 周） | 评测集：数十条真实口播加人工剪辑标注；IR v1 的 Zod schema；引擎对照结果 | 百炼 filetrans 与火山极速版对比；用同一批素材对照 Remotion 和 HyperFrames | 有删除候选精确率/召回率的基线；主引擎定案 |
| 1：口播 MVP（6–8 周） | 上传→ASR→规则+LLM 剪辑→剪后重对齐字幕→包装→渲染→剪映草稿 | 云 ASR；Qwen 或 DeepSeek 结构化输出；在国内云容器自托管 Remotion；Postgres + BullMQ/Celery；transcript 编辑器 + Player；`loudnorm` | 每分钟成片的人工复核时长明显低于手工剪辑 |
| 2：文案视频 + 合规（6–8 周） | 分镜→逐句 TTS→素材→模板→BGM；AIGC 显式与隐式标识；抖音发布 | CosyVoice v3.5；Pexels + AI 图 + 少量 AI 视频钩子；10 个左右模板；自有曲库；按 TC260 写元数据 | 模板覆盖主要内容类型；标识可审计 |
| 3：质量与成本（8–12 周） | punch-in 与重构图、B-roll 检索重排、VLM 质检、降噪、授权数字分身 | MediaPipe、jina-clip-v2、qwen3-vl、DeepFilterNet3；自托管 Qwen3-ASR 和 CosyVoice3；迁移到 Temporal；KEDA 扩缩容；FFmpeg 快速路径 | 单位成本和返工率达到目标 |
| 4：规模化与扩展（持续） | 长转短、多平台版本（9:16/16:9、不同时长与响度）、agent 研发模板 | 切片打分细则；用 HyperFrames 研发模板；多租户公平调度 | — |

阶段 0 最容易被跳过，但它决定了后面每个阶段能否量化进展：两个引擎的公开对比互相矛盾，只有在自家素材上实测才能定案；“LLM 去重复”的准确率和召回率没有任何公开评测，只能靠自建标注集衡量；ASR 厂商的 WER 几乎都是自报数字，同样需要在自家素材上复测。阶段 1 刻意选择托管 API 和单机渲染，不碰 GPU 和分布式；让同一份 `pipeline(steps)` 定义既能在本地脚本里顺序运行，也能被队列 worker 分步执行，可以避免过早引入复杂度。阶段 2 把合规模块和文案视频一起上线，因为文案视频天然含 TTS，从第一条成片起就需要标识。

## 结论

这套系统真正的护城河不是渲染引擎，而是 IR 和沉淀在其上的决策数据。用户每一次“恢复这段”或“这里也删掉”，都是一条带标签的剪辑偏好样本，可以用来调规则阈值、做 LLM 提示词的 A/B 测试，将来甚至训练专用模型。渲染引擎则应该可以替换：video-use 和 OpenMontage 已经同时支持 Remotion 和 HyperFrames，HyperFrames 还提供了 Remotion 迁移 skill，今天选 Remotion 是为了降低风险，而不是为了长期绑定。同理，单位经济的主杠杆不是把渲染从几毛钱压到几分钱，而是把人工复核从“整片重看”压到“只看低置信度片段”，所以置信度、原因标注和人工锁定这些字段应该从 IR v1 起就是一等公民。

有几件事会改变本报告的结论，值得持续跟踪：Remotion 5.0 授权条款的最终文本（外包计入人数、强制遥测）、HyperFrames 何时走出 0.x 以及它在中文字体和长素材上的稳定性、OpenCut 的无头模式和 MCP 是否发布、剪映草稿格式会不会进一步封闭，这四项影响选型；抖音开放平台是否增加 AIGC 声明字段、GB 45438 对显式标识的量化要求，这两项影响合规实现。IR 引擎无关、剪映导出定位为尽力而为、合规模块默认开启，正是为了让这些变化发生时，只需要换掉一个适配器。
